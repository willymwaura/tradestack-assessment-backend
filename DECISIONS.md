## Model Design Decisions

### 1. Receipt Identity

* Use `receipt_ref` as the unique business identifier for a collection.
* Enforce a database uniqueness constraint on `receipt_ref`.
* Reason: It is the most appropriate field for preventing duplicate receipt processing.

### 2. Client UUID

* Store `client_uuid` but do not use it as the unique identifier.
* Reason: It appears to be a client-generated identifier and may not uniquely identify a business receipt.

### 3. Conflict Resolution Timestamp

* Store `recorded_at` exactly as received.
* Use it to implement the required last-write-wins behavior.
* Reason: The contract explicitly specifies conflict resolution using `recorded_at`.

### 4. Receipt Device ID

* Store the receipt-level `device_id`.
* Reason: The sample data contains receipt-level device IDs that differ from the batch-level device ID and provide better audit information.

### 5. Server Receipt Timestamp

* Add a `received_at` field generated by the server.
* Reason: To track when the backend actually received the collection and measure synchronization delays.

### 6. Collection Audit History

* Maintain an audit trail instead of overwriting data without traceability.
* Reason: To preserve a history of changes and support investigations.

### 7. Audit Scope

* Audit all processing outcomes:

  * `CREATED`
  * `UPDATED`
  * `IGNORED_OLDER_VERSION`
  * `DUPLICATE_BATCH`
* Reason: To provide full visibility into server decisions.

### 8. Current State + History

* Keep the latest version of a collection in the `Collection` table.
* Store historical events in a separate audit table.
* Reason: Supports both efficient queries and historical tracking.

### 9. Outlet Relationship

* Use a foreign key from `Collection` to `Outlet`.
* Reason: Outlet data is already managed and seeded separately.

### 10. Database Indexes

* Add indexes on:

  * `recorded_at`
  * `outlet`
* Reason: These fields are used by the listing and filtering endpoints.

### 11. Batch Tracking

* Create a `CollectionBatch` model to store batch metadata.
* Reason: The requirements state that the system must be able to see what happened to a batch after processing.

### 12. Batch Audit

* Maintain audit records for batch processing events.
* Reason: To track duplicate batches and processing outcomes.

### 13. Preserve Both Device IDs

* Store both the batch-level `device_id` and the receipt-level `device_id`.
* Reason: The sample payload contains both, and retaining them avoids losing audit information.
### Duplicate Batch Detection

The contract states that a handset may retry an entire batch if it does not receive a response. To prevent duplicate processing, I generate a deterministic SHA-256 hash from the incoming batch payload and store it in the CollectionBatch table.

If a batch with the same hash is received again, it is treated as a duplicate retry and is not reprocessed.

This approach requires no additional client-generated identifiers and directly addresses the retry behavior described in the specification.

### Collision Detection

I defined a collision as an incoming collection whose `receipt_ref` already exists in the system.

When a collision occurs, the contract's last-write-wins rule is applied using `recorded_at`:

- If the incoming record has a newer `recorded_at`, the existing collection is updated.
- If the incoming record has an older or equal `recorded_at`, the incoming record is ignored.

This behavior is recorded in the audit log.

### Amount Validation

Collections must have an amount greater than zero. Requests containing zero or negative amounts are rejected because they do not represent valid collection receipts.
### Duplicate Receipt References Within a Batch

A batch may not contain the same receipt reference more than once. Such requests are rejected because they create ambiguity during conflict resolution.

### Transaction Management

Batch processing is performed inside a database transaction. If any unexpected processing error occurs, the entire batch is rolled back to avoid partial writes.
### Batch Processing Response

The batch endpoint returns a processing summary including the number of created, updated and ignored receipts. This allows operators and clients to understand what action was taken.

### Duplicate Batch Handling

Duplicate batches return HTTP 200 rather than an error response. The retry behavior is expected according to the contract and is treated as a successful idempotent operation.
